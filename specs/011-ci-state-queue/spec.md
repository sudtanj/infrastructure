**Feature Branch**: `011-ci-state-queue`

**Created**: 2026-11-28

**Status**: Draft, amended 2026-11-28 by the owner rule "Amend 011", corrected the same day (the ban covers files under `.github/workflows/` and `.github/scripts/` only), and amended again the same day by the owner's tick decisions (scheduled pipelines return and run through the tick; state, queue and artifacts move to the tick path; see the last Clarifications session of that name, which supersedes every line that disagrees)

**Input**: User description: "Run the `ci` pipelines on a schedule from reviewed config, queue runs that share a state strictly first in, first out, restore and save a pipeline's state (a Playwright storageState file) in an encrypted release on the private repo that owns the pipeline, and upload encrypted debug artifacts to that repo on failure. ## Who this is for

The owner, who runs `factory-monorepo-ci` and writes the `.factory-ci.toml` files of the watched repos, and the AI agent the owner sends to debug a failed run. The first user is the Playwright browser-test project (spec 002 in `sudtanj/factory-monorepo`), which logs in to the owner's own sites with human-like input. A standing rule of the owner binds the whole feature: no AI agent ever sees a Bitwarden credential, and a pipeline step receives only the values it declared. The agent gets two things only: the artifact key and a Loki read token.

## Problem

`ci` starts only by hand, forgets everything between runs, and cannot say why a browser test failed. Evidence:

- `.github/workflows/factory-monorepo-ci.yml` has `workflow_dispatch` as its only trigger. The concurrency group is `factory-monorepo-ci-<repo>-<ref>-<project>` with `cancel-in-progress: false`. GitHub keeps one running and one pending run per group and cancels an older pending run when a third arrives, so a queue of three loses a run. The owner rule of 2026-11-28 keeps this file as it is, so the group, the 45-minute job limit and the image pin stay.
- `rust-ci-runner/src/ci.rs` fetches the branch into a new directory under `--work`, runs the pipeline and removes the directory (`remove_ws`). Nothing survives. A browser test that logs in with a username and password every run looks like a bot to the target site and may trip captchas or lockouts. It needs its cookies back.
- The public Actions log shows only fixed lines (`log.rs`). The step output that explains a failure goes to Loki, and a Playwright failure is mostly a trace and screenshots, which Loki lines cannot carry. An agent has nothing to read.
- A GitHub release asset on a private repo is downloadable by everyone with read access to that repo, so a cookie file stored there unencrypted is a session theft waiting for a read-only collaborator or a leaked read token.
- `FACTORY_CI_TOKEN` is read-only by design (spec 008). Writing a release needs a second token with contents write.

## Announcement

Pipelines run by the tick can now run on a schedule, remember their state and leave evidence when they fail. A project declares `[schedule]` with `every = "6h"` in its `.factory-ci.toml`. The tick, which the outside dispatcher starts about every 5 minutes, looks at the private store repo: a slot that is due and has no claim runs on the next tick. Missed slots coalesce into one run, and the same slot never runs twice, because the run writes its claim as a release asset whose name is the slot, and GitHub refuses a second asset of the same name. The same tick `job` restores the `[state]` file just before the one step that declares it, saves the new copy after a passing run, queues runs that share a state, scans and encrypts the declared artifacts and uploads them when a run fails. All of it runs only on branch `main` of a watch entry that says `secret_branches = ["main"]`; other branches run as before, with none of it. The store token and both keys are runner-only: the frozen tick script hands them to the runner through its names file, the runner reads them once and removes them from its environment, and a step can never request them. The manual `factory-monorepo-ci.yml` stays as it is with its pinned 0.3.0 runner; it cannot run a project that uses the new keys, and the README says so. The new binary reaches the tick with `gh variable set RUNNER_IMAGE_DIGEST` (T039) and no workflow edit.

For a scheduled row that would write `error` on the push context and the push walk would retry that sha 30 minutes later (`walk.rs:104`). Chosen fix: `job::status` reads the latest own status of the push context first and routes by it (FR-073). The plan posts `pending` on the push context for every push row before it keeps the row, so a push row always has `pending` there when the fallback runs; anything else is a scheduled row and its `error` goes to `factory-ci-schedule[/<project>]`. Why not the marker file `$RUNNER_TEMP/fci-sched-<run_id>`: the script refuses and the status step can run before the runner starts (`job.sh:30-45`: no runner, a failed blob decrypt, the `iptables` call), so no marker exists yet; a stale marker can also survive a rerun. - Q: M2, a half-created claim? -> A: On a 4xx the job lists and compares (FR-003): ours is created; `uploaded` and not ours is lost; not `uploaded` and older than 360 s is deleted and the create retried once; younger means another job is uploading. `plan` ignores a not-`uploaded` claim older than 360 s, so it cannot block a slot.
- Q: M3, a failed finish repeats a passed slot? -> A: The label is set right after `run_pipeline`, before bundle, scan and uploads, and honours the rate-limit pause (FR-003).
- Q: M4, the signal path? -> A: Delete the claim only while it is `r` and no step has completed; otherwise `PATCH` `f` (FR-064).
- Q: M5, the release create race and the ambiguous 404? -> A: The owner seeds `ci-sched+<owner>_<name>` once (owner actions). `plan` reads a 404, a 403 or an unreadable store as a problem, never as an empty ledger; the job re-fetches 3 times (1 s, then 2 s) (FR-063, FR-003).
- Q: M6, long scheduled runs starve push CI? -> A: A scheduled pipeline is capped at 10 minutes (FR-070), the floor stays 15 minutes, the cost is stated in R22 and the README, and an alert fires on a tick longer than 20 minutes (FR-071). New owner call O21: the 10-minute cap.
- Q: N-items? -> A: N1 a `schedule silent exit` Loki line and an alert on more than 3 in a row (FR-071). N2 claims order by the `(slot, n)` of the name (FR-063). ### Session 2026-11-28 (owner tick decisions; this session supersedes every earlier line that disagrees)

Reading rule: wherever an older line says `ci` for the queue, state, artifacts, vault, attempt number or image, read the tick `job` path. The manual `ci` path refuses those declarations (FR-069). Where an older line says the run prints a fixed line to stderr, the tick instead puts the same fixed text, with no name, in the commit status description (the tick prints nothing public: `--quiet-logs`).

- Q: What did the owner decide? -> A: Decision 1: "I think we need to save the state to private repo on the release tag so the ci just run in interval of 5 minutes to check what toml it hasnt pickup on all repo listed." Then: "Please keep the state since if there is a scheduled toml not run it should run on next interval and remember to avoid multiple execute same as on push." Decision 2: on the tick only the factory-monorepo `main` branch gets declared step secrets, saved state and vault fields; other branches run without them.
- Q: Which path now carries the features? -> A: The tick. The `job` subcommand restores, queues, saves, bundles and claims; the `plan` subcommand decides which schedule slots are due. The manual `ci` workflow keeps its frozen pin (0.3.0) and refuses the new declarations (FR-069). 011 no longer depends on moving that pin.
- Q: What does a schedule look like? -> A: A table in the project's `.factory-ci.toml`: `[schedule]` with `every` (an integer and one unit `m`, `h` or `d`, from `15m` to `31d`) and an optional `offset` (same form, or `0`, smaller than `every`). Time is UTC. A slot is an instant `t` with `t = offset (mod every)` counted from the Unix epoch, so `every = "1d"` with `offset = "3h"` is 03:00 UTC daily, and `6h` is 00, 06, 12 and 18 UTC. No cron text, no time zone, no daylight saving. The floor is 15 minutes, above the 5-minute minimum the owner set, because the tick runs about every 5 minutes (a shorter interval fires on nearly every tick) and the store allows 500 content writes an hour. Anything else is refused (FR-001).
- Q: Who reads the ledger and who writes it? -> A: `plan` reads, the run job writes. Evidence, all in the frozen files: the plan job holds `FACTORY_CI_TOKEN` and the bws tokens (`factory-ci-tick.yml:96-110`); `factory-ci-plan.sh:35-37` strips the bws tokens from the plan runner's environment and `:66` exports only the three log values, which `fci_log_creds` fixes by name (`factory-ci-secrets.sh:84-100`). No mechanism hands the plan runner a write token. The run job does have one: `factory-ci-job.sh:55-66` lets the runner's prepare mode list names, `:68-71` demands `secrets_ok` for any name, `:73-101` resolves each name from the per-repo key `<repo>/<NAME>` (`factory-ci-secrets.sh:71`) and exports it, `:115-117` unsets the bws token and `exec`s the runner. The runner's prepare mode therefore lists `FACTORY_CI_STATE_TOKEN` (and, when the pipeline needs them, the two keys and the vault credentials) in the names file, and `plan` sets `secrets_ok` (FR-066).
- Q: Why can a slot not run twice? -> A: Ticks never overlap: the group `factory-ci-tick` with `cancel-in-progress: false` (`factory-ci-tick.yml:9-11`) lets a tick finish, `run` jobs included (`verdict` needs them), before the next `plan` starts. A claim is one release asset named `claim-<h16>-<slot>-<n>`; creating it is atomic because GitHub refuses a second upload with the same name. A rerun of an old tick, two items for one slot and a manual dispatch all meet that refusal. The run job claims after it holds its queue turn, so a run that never starts leaves no claim and the slot stays due.
- Q: What if the run job dies after it claimed? -> A: The claim label says `r` (running) with the epoch. A claim still `r` after 3600 s is stale (the job limit is 45 minutes and the claim is written inside the job, so a live run cannot be older than that). The next tick runs the slot once more as attempt `n = 1`; a stale `n = 1` closes the slot with an `error` status and no third run. A cancelled job (SIGTERM) deletes its claim, so the next tick runs the slot at once. This mirrors the push walk's stale `pending` rule (`walk.rs:11`, 7200 s), with a shorter constant because the claim is written at turn time, not at plan time.
- Q: How do scheduled runs post statuses without colliding with push runs? -> A: Scheduled rows are marked by `prev_sha == sha` (a push row's `prev_sha` is an ancestor or empty), `plan` posts no `pending` for them, and the run job posts one final status to its own context `factory-ci-schedule` (root project) or `factory-ci-schedule/<project>`. No push context equals it or starts with it, because push contexts are `factory-ci` or `factory-ci/<folder>` (`projects.rs:22-26`). It posts only when the outcome differs from the previous claim's outcome (or there is none) and the latest own status of that context on the sha is at least 1 hour old; an HTTP 422 (the 1000-status cap) is logged and ignored. A repeated pass or a repeated fail posts nothing. A scheduled run on an unchanged sha runs, because the plan decides it from the ledger and never reads the push statuses.
- Q: A push row and a scheduled row for one project in one tick? -> A: The push row wins. The scheduled row is dropped for that tick, its slot stays due and runs on the next tick. At most one row per (repo, branch, project) exists per tick, so the tick queue seldom has two waiters; the queue stays because the owner asked for it.
- Q: How big is the ledger and how is it kept consistent? -> A: No shared document is ever read, modified and written. One claim, one 1-byte asset, written once by its creator and changed only by its creator (`PATCH` of the label). `plan` only lists. The cleanup after a finished claim deletes, for the same `<h16>` only, all but the 2 newest `uploaded` claims, and deletes any claim of any `<h16>` whose label epoch is more than 90 days old. A list of more than 300 assets fails closed: `plan` emits no scheduled row and reports a problem. `<h16>` is the first 16 hex characters of SHA-256 over `project`, a NUL byte and `branch`.
- Q: Where is the store repo and how does `plan` learn its name? -> A: The plan runner cannot read Bitwarden, and a new watch key is impossible (next answer). The store is `<owner>/factory-ci-state`, where `<owner>` is the owner of the watched repo, in code, for both the `plan` read and the `job` write. The `FACTORY_CI_STATE_REPO` setting stays reserved and, on the tick, the job refuses a value that differs from the derived name. The name of a private repo is as public as the names of the watched repos in the watch file. `FACTORY_CI_TOKEN` needs contents read on the store repo (owner action). If the store repo or the read fails, `plan` emits no scheduled row (fail closed) and reports a problem.
- Q: Which watch keys? -> A: None new. `state` and `vault_items` are dropped: the pinned 0.3.0 refuses unknown watch keys (`watch.rs:12-19`, `:168`) and both `ci` (frozen pin) and the tick read `.github/factory-ci-repos.toml`. `secret_branches` already parses in 0.3.0 (`watch.rs:16`, `:203-205`). Decision 2 reads: the tick grants the store, state, queue, artifacts, vault and declared step secrets only when the row's branch is `main` and the entry's `secret_branches` is exactly `["main"]` (a glob or a longer list does not count) and the repo is private. `plan` sets `secrets_ok` from that rule (OR 012's image rule). The vault allowlist is dropped: only code on `main` can declare a vault field, the collection-limited account bounds what it can see, and the job reads only declared pairs. Adding the key to the `factory-monorepo` entry is safe under 0.3.0 (the 0.3.0 plan ignores it; the frozen manual `ci` then honours it for declared step secrets, as 010 intends).
- Q: What does 0.3.0 refuse? -> A: The pipeline file keys. `pipeline.rs:10` and `:29` use `deny_unknown_fields`, so a `.factory-ci.toml` with `[schedule]`, `[state]`, `[artifacts]`, `state = true` or `vault` is refused by 0.3.0 `job` and `ci`. Order: release, set `RUNNER_IMAGE_DIGEST`, watch a tick, then add the keys to the project toml. The frozen manual `ci` then cannot run that project (`pipeline file refused`). The owner accepted a frozen pin; the README says this.
- Q: How does the tick runner learn its attempt number, run id and helper image? -> A: It runs on the VM, not in a container (`factory-ci-tick.yml:152-160` copies the binary out of the image), so D19 (`docker inspect` of its own container) does not apply. Attempt: `GITHUB_RUN_ATTEMPT` (set by Actions, inherited at `job.sh:117`), digits else `1`. Run id of tickets and asset names: the row's `--run-id` (16 hex, set by `plan`, unique per row), so matrix siblings never share one. Helper image for the `chown` backstop: `FACTORY_CI_CLONE_IMAGE`, already required pinned and passed to the `job` step (`factory-ci-tick.yml:200`); a clone image without `chown` and `chmod` ends the run `runner fault`.
- Q: Which rows get schedules? -> A: Only `main` of a private repo with `secret_branches = ["main"]`, `allow_docker = false`, and a project that is not `docker/<name>` (feature 012). Schedules elsewhere are ignored, counted in the plan summary without names. The tick `run` job's Environment (`factory-ci`) and its 45-minute limit apply to scheduled runs as to push runs; the Environment must allow `main` (owner check).
- Q: How do 011 and 012 merge? -> A: 012 first (S2 is committed at 6631734; it already holds the `secrets_ok` expression, `secret_names` and the job deadline). 011 code rebases on it. The overlap is in `plan.rs` (the `secrets_ok` line, rows), `job.rs` (`target`, `secret_names`, `attempt`), `engine.rs` and `projects.rs` (`context`, project paths). The 011 spec, plan and task documents merge independently now.
- Q: Does the queue still make sense? -> A: Seldom needed on the tick (serial ticks, one row per project per tick). It stays by the owner's word and is the guard for tick reruns; the owner can drop it with no effect on the rest (R17).
- Q: Which calls stay open for the owner? -> A: Four, each with the default this spec uses until the owner answers: (1) the store repo name is derived in code as `<owner>/factory-ci-state` (alternative: none that works, since the plan runner cannot read Bitwarden and the watch file takes no new key); (2) schedules run on `main` only (alternative: tier-1 token for every scheduled branch, which needs `secrets_ok` on all scheduled rows and widens token exposure); (3) a project that uses the new keys cannot run through the frozen manual `ci` (alternative: unfreeze the pin, which the owner ruled out); (4) a scheduled pipeline is capped at 10 minutes (alternative: raise the cap or the floor, at the cost of push-CI latency on the serial tick). ## User Scenarios & Testing *(mandatory)*

### User Story 1 - The browser test keeps its login between runs (Priority: P1)

The owner declares a `[state]` file in the Playwright pipeline and sets `state = true` on the `sudtanj/factory-monorepo` watch entry. Run 1 starts with no state, logs in, passes and saves the cookie file. Run 2 restores it and skips the login.

**Why this priority**: It is the reason for the feature. Without a restored session every run logs in again.

**Independent Test**: A fixture pipeline whose step writes a counter into the state file. Mock the GitHub API and the key store. Run `ci` three times. The step sees 0, 1, 2. The mock holds only encrypted bytes, and none of the plaintext.

**Acceptance Scenarios**:

1. **Given** no state release exists, **When** `ci` runs a pipeline with `[state]`, **Then** the state file is absent at step start, the pipeline passes, and an encrypted asset exists afterwards.
2. **Given** a state release with one asset, **When** `ci` runs, **Then** the decrypted file is at the declared path before the first step starts.
3. **Given** the pipeline fails, **When** the run ends, **Then** the stored state is byte for byte the one before the run.

### User Story 2 - Runs of one state never overlap and run in order (Priority: P1)

Two runs start together for the same state. Both run, one after the other, in order, as far as GitHub starts both.

**Why this priority**: Two runs that share a state would restore the same cookies and overwrite each other's save, or log in twice from two places.

**Independent Test**: Mock store. Start four `ci` processes for one state. Assert the pipeline windows do not overlap and the order equals the ticket order. A fifth waits as well; only a run that cannot get a turn before its wait limit ends with `queue wait expired`. The test runs the queue on a fake store with test timing, so the 5-minute wait of production does not limit it.

**Acceptance Scenarios**:

1. **Given** run A holds the turn, **When** run B and C register, **Then** B starts after A ends and C after B ends, and each prints `[runner] waiting for the queue` once.
2. **Given** A's runner is killed, **When** 10 minutes pass without renewal, **Then** B removes A's ticket and starts.
3. **Given** the turns ahead of a waiter use up its wait limit (the budget end minus 30 minutes), **When** that point passes, **Then** it removes its own ticket, prints `[runner] queue wait expired`, exits 1 and starts no step. This is the one drop the runner makes; GitHub's concurrency group, which stays, can also cancel a pending run before the runner starts. The owner's Grafana alert on this line is built by hand.

### User Story 3 - A declared schedule runs on the next tick, once (Priority: P1)

The owner adds `[schedule]` with `every = "6h"` to the Playwright project's `.factory-ci.toml`. At the next tick after 06:00 UTC the project runs, whatever the commit did. **Acceptance Scenarios**:

1. **Given** a declared artifact holds a known secret value in a zip entry, **When** the run ends, **Then** nothing is uploaded, stderr shows `[runner] artifact upload refused` and the exit code is 1.
2. **Given** an artifact with no known value in it, **When** the run ends, **Then** it is encrypted with the artifact key and uploaded, and the state key cannot open it.
3. **Given** an artifact path that is, contains or lies under the state path, **When** the pipeline is read, **Then** the run ends with `[runner] pipeline file refused`.

### Edge Cases

Answers to the edge-case checklist. "Handled" names the requirement.

- Inputs. State or artifact path absolute, with `..`, through a symlink, or outside the project: pipeline refused (FR-018). Two `[state]` tables: TOML error, refused. State name with `/`, uppercase, Unicode, NUL, over 64 characters: refused (FR-018). State file empty, over 10 MB, or missing after a pass: no save, `state save failed` for the oversized one, a Loki line for the missing one (FR-024). Artifact path that matches nothing: skipped, a Loki line. Bundle over 100 MB: not uploaded, a Loki line (FR-032). A project name with `..`, ending in `.` or `.lock`, used with `[state]` or `[artifacts]`: pipeline refused (the release tag would be invalid).
- State. First run with no state starts empty (FR-021). A crash between upload and delete leaves two assets, and the newest wins (FR-025). A truncated or tampered asset, or the wrong key: restore fails and the run stops, with state untouched (FR-022). Older asset format: no older version exists. A retry is safe: ticket and asset names carry the run id, so a rerun of the same run id replaces its own ticket and saves one new asset.
- Partial failure. Restore fails: no step starts, the ticket is released. Pipeline fails: state kept, artifacts uploaded, ticket released. Save fails after a pass: the run fails, the ticket is released, the old state stays (FR-026). Artifact upload fails: Loki line, exit code unchanged (FR-031). Release of the ticket fails: the stale rule frees it within 10 minutes (FR-014).
- Time and concurrency. Two runs register together: the store decides the order, and the order is stable (FR-010). Every GitHub call has a time limit and one retry on no answer or 5xx; a 403 or 429 pauses all calls (FR-036). Clock skew between runners: ticket age comes from the GitHub server time, never the runner clock (FR-013). A cancelled pending run (the concurrency group stays): not recoverable by the runner (R4). A job that hits the 45-minute limit: the budget end sits 10 minutes before it, so the runner ends first.
- Resources. Waiters poll every 20 s, so each waiter costs about 3 calls a minute against the token's 5,000 an hour. Releases hold at most 2 state assets and 10 artifacts per project. A waiting job holds one hosted VM for at most 5 minutes of waiting (R7).
- Trust. Who can name a state: the pipeline author, inside the repo's own releases, only when the reviewed watch entry says `state = true` with `secret_branches = ["main"]` and the repo is private, in a store repo that holds no code. Who can reach the token: the runner process only. What the pipeline author cannot do: write another repo's release, read a setting or a vault credential, widen an entry, choose a release tag outside the fixed naming (FR-019, FR-034, FR-042). What the agent cannot do: open state, because it holds neither the state key nor the token (FR-027, FR-048).
- Vault and scan inputs. A vault item that matches zero or more than one login in the allowed collection, a missing field, an empty field, a value with NUL or with a trimmed line under 4 characters, or a locked or revoked identity: `vault unavailable`, no container (FR-045). Two steps declaring the same environment variable for different fields, or one that also appears in `env` or `secrets`: pipeline refused (FR-042). An item name with Unicode, spaces or `=`: allowed, matched by exact bytes, and passed only through the environment, never argv. A zip with an encrypted entry, nesting deeper than 2, an entry count over 10,000 or more than 500 MB uncompressed: not scannable, so no upload (FR-049). A value split across two lines or transformed beyond base64 is not found (R2, R11).
- Vault resources and failure. The `bw` call has a time limit and one retry (FR-036). A `bw` that hangs or crashes leaves its data directory, which the runner removes anyway (FR-046). A vault that lock or logout fails on ends the run (FR-046).
- UI. No UI. The surface is the fixed stdout and stderr lines (FR-037).
- Schedule and claims. A slot boundary (the tick at 05:59:59 and 06:00:00), `every` at 15m and 31d, `offset` equal to `every` (refused), a clock a minute off between plan and job (the job recomputes `due` and claims whichever slot it sees; the next plan sees that claim), two jobs for one slot (one create wins), a run job that dies before the claim (the slot stays due), a run job that dies after it (stale at 3600 s, one retry, then closed), a cancelled tick (claim deleted), a store outage at plan (no row, one problem), a store outage at claim (the job ends before it runs; the slot stays due), an unchanged sha with a passing push status (still runs), a branch deleted (its claims age out in 90 days), more than 300 assets (fail closed), a label forged by someone with write access to the store (malformed or future: stale, and the retry cap bounds the harm to two extra runs of one slot). Added by the critic review: a half-created claim (deleted after 360 s, never blocks the slot), a failure before the claim (error status backoff of min(every, 1 h)), a cancelled job that already ran a step (label f, not deleted), a cancelled retry attempt n=1, a status fallback for a scheduled row (schedule context only), a 2 s Date skew at a slot boundary, a missing ledger release or a 403 on the tag (a problem, never an empty ledger), and a ledger outage while push rows are due (push rows still run).

## Requirements *(mandatory)*

Each requirement is an acceptance criterion in the form WHEN trigger THE SYSTEM SHALL response. Tags: `[error]` is a failure path, `[boundary]` is an edge of an allowed range. Each maps to at least one unit test under `cargo test --lib` (Principle V); file-format checks run in the `rust-ci-runner` pipeline. No workflow or script check changes.

### Functional Requirements

**Schedule**

- **FR-001** `[error]`: THE SYSTEM SHALL accept one optional table `[schedule]` in `.factory-ci.toml` with `every` (regex `^[1-9][0-9]{0,4}[mhd]$`, 900 s to 2,678,400 s) and optional `offset` (regex `^(0|[1-9][0-9]{0,4}[mhd])$`, smaller than `every`), and no other key. WHEN the table, a value, a unit, a bound or a key is wrong THE SYSTEM SHALL refuse the pipeline file (`pipeline file refused` in `job` and `ci`; a plan problem plus one `error` status on `factory-ci-schedule[/<project>]` per sha for `plan`). `[boundary]` `15m` and `31d` pass, `14m` and `32d` fail; `offset` equal to `every` fails.
- **FR-002**: WHEN `plan` runs THE SYSTEM SHALL, for each watch entry with `allow_docker = false` and `secret_branches` exactly `["main"]` whose repo is private, read the `.factory-ci.toml` of each non-`docker/` project at the tip of `main`, validate the whole file with the pipeline parser (`pipeline::parse`, the same checks `load_pipeline` runs on text), read the ledger of the repo, take `due = now - ((now - offset) mod every)` with `now` from the `Date` header of the ledger answer, and plan one scheduled row when the newest claim of the project (ordered by the `(slot, n)` parsed from its name) is below `due` or stale (FR-064), and no backoff applies. Backoff: WHEN the latest own status of the schedule context on the tip is `error` and younger than `min(every, 3600 s)` THE SYSTEM SHALL plan no row for the project. A file that fails the parser, or has a bad `[schedule]`, gives a problem line and one `error` status on the schedule context, and no row. Missed slots coalesce: only `due` is considered. A schedule that never ran is due at the next tick. At most one row per (repo, branch, project) and tick; a push row for the same project wins and the scheduled row waits (FR-068). Schedules on other branches, other entries and `docker/<name>` projects are ignored and counted in the summary without names. A blob read is skipped when another project of the tick has the same blob sha (the tree listing carries it); a read that would pass 40 per tick marks the repo `unchecked` for that tick.
- **FR-003**: WHEN a scheduled row runs THE SYSTEM SHALL take its queue turn first (when the pipeline has `[state]`), then recompute `due` from the server time, create the claim asset `claim-<h16>-<due>-<n>` in release `ci-sched+<owner>_<name>` of the store, and only then restore state and run. A failure after the claim leaves the label `f`, so no failure after the claim repeats the slot. On a 4xx from the create THE SYSTEM SHALL list the release and compare the asset of that name: `uploaded` and not ours (the label's run id differs) means lost, end silently; ours means created; not `uploaded` and older than 360 s means delete it and retry the create once; not `uploaded` and younger means another job is uploading, end silently. The label is `r.<epoch>.<runid>` at creation and `p.` or `f.` at the end, changed only by the creator. The creator sets `p` or `f` right after `run_pipeline` returns, before the bundle, scan and uploads, so a late failure cannot repeat a passed slot; the label write honours the rate-limit pause of FR-054 (at most 120 s) and is tried 3 times, then logged as `claim finish failed`. The release is seeded by the owner (FR-063); if the tag lookup answers 404 the job fetches it again 3 times, waiting 1 s and then 2 s, and ends `state store not configured` if it is still absent.
- **FR-004**: WHEN a scheduled run ends THE SYSTEM SHALL post at most one status, to `factory-ci-schedule` (root) or `factory-ci-schedule/<project>`, on the sha it ran. An `error` always posts (it is the backoff signal of FR-002, and the plan runs the project again no sooner than `min(every, 3600 s)`). A `success` or `failure` posts only when it differs from the previous claim's outcome of the same `<h16>` (or there is none) and the latest own status of that context on the sha is at least 3600 s old. An HTTP 422 is logged and ignored. No `pending` is posted and no push context is written.
- **FR-005**: WHEN a run starts by manual dispatch THE SYSTEM SHALL behave as before, with the same inputs and the same command line. `ci` takes no `--entry` flag. A run that declares the new keys is refused by the frozen pin before it reaches this runner; a 0.4.x `ci` refuses it by FR-069.

**Queue**

- **FR-006**: WHEN a pipeline declares a `[state]` and passes the file, docker and secret checks THE SYSTEM SHALL register one ticket in the queue of that state in the store repo, before restoring state or starting any container. A pipeline with no `[state]` registers nothing.
- **FR-007**: WHEN a ticket is first in line THE SYSTEM SHALL let its run restore, run and save. WHEN it is not THE SYSTEM SHALL start no container and touch no state, poll every 20 s, and print `[runner] waiting for the queue` once to stdout.
- **FR-008**: WHEN several tickets exist THE SYSTEM SHALL run them in registration order, one at a time. The turn passes only after the previous run released its ticket or its ticket went stale. No ticket is skipped, reordered or dropped except by FR-011, FR-012 and FR-014.
- **FR-009**: WHEN a run ends, whatever the result (pass, fail, refusal after registering, panic, SIGTERM, SIGINT) THE SYSTEM SHALL remove its ticket before exit. A cancelled GitHub job sends SIGTERM and the runner gets its grace period to do so.
- **FR-010**: WHEN two runs register at the same moment THE SYSTEM SHALL give them one stable order decided by the store, the same for both.
- **FR-011**: THE SYSTEM SHALL NOT cap the number of tickets of a state; a run that registers waits for its turn. A broken ticket that is deleted and registered again goes to the back; that is an accepted residual. The runner cannot recover a run that GitHub's concurrency group (kept) cancels before the runner starts.
- **FR-012** `[error]`: WHEN a run has not won its turn by the budget end minus 30 minutes (5 restore, 10 minimum pipeline window, 15 reserve) THE SYSTEM SHALL remove its ticket, print `[runner] queue wait expired`, exit 1 and start no container. The budget end is the runner start plus 35 minutes unless the environment sets `FACTORY_CI_BUDGET_END` (tests); the job limit is 45 minutes and equals `timeout-minutes` of the workflow (a test reads the file). `[boundary]` One second before the point the run keeps waiting.
- **FR-013**: WHEN a run keeps a ticket THE SYSTEM SHALL renew it every 60 s, waiting or running, using the store's server time to judge age, never the runner clock.
- **FR-014** `[error]`: WHEN a ticket has gone 10 minutes without renewal THE SYSTEM SHALL treat it as stale, let the next waiter remove it and log the removal to Loki as step `ci`. `[boundary]` 9 minutes 59 seconds is not stale, 10 minutes is. A holder whose renewals have failed for 600 s stops its run (FR-054).
- **FR-015** `[error]`: WHEN a run finds its own ticket gone before it saves state THE SYSTEM SHALL write nothing, end the run with exit code 1 and `[runner] state save failed`, and log the cause to Loki.
- **FR-016**: WHEN waiting runs show anything publicly THE SYSTEM SHALL show only the line of FR-007. Positions, ticket names, ages, state names and repo names go to Loki as step `ci` only.

**Declaring state and artifacts**

- **FR-017**: THE SYSTEM SHALL accept two optional tables in `.factory-ci.toml`: `[state]` with `name` and `path`, and `[artifacts]` with `paths` (a list) and `when` (`"failure"` or `"always"`, default `"failure"`), and the step key `state = true`, carried by exactly one step when `[state]` exists and by none otherwise. Unknown keys stay errors.
- **FR-018** `[error]`: WHEN `name` is not 1 to 64 characters of `[A-Za-z0-9_-]`, or `path` or an artifact path is empty, absolute, contains `..`, a NUL or a newline, or resolves through a symlink or outside the project folder, or a list holds more than 20 paths, or an artifact path equals, contains or lies under the state path, or `[state]` has no step with `state = true` or more than one, or another step is neither a transitive dependency nor a dependent of the state step (it could run beside it), or a name in `env`, `secrets` or a vault `env` starts, in any letter case, with `BW_`, `BWS_`, `BITWARDENCLI` or `FACTORY_CI` THE SYSTEM SHALL end the run with `[runner] pipeline file refused` and start no container. `[boundary]` A 64-character name and 20 paths are accepted, 65 and 21 are not. A sibling path that only shares a prefix with the state path (`.ci-state` and `.ci-state-2`) is accepted.
- **FR-019** `[error]`: WHEN the tick `job` runs a pipeline that declares `[state]` or `[artifacts]` and the row is not allowed the store (the branch is not `main`, the entry's `secret_branches` is not exactly `["main"]`, or the repo is public) THE SYSTEM SHALL run the pipeline as before 011 with no ticket, restore, save, bundle or store call; `job` prepare lists no runner-only name for a branch other than `main`. WHEN the branch is `main` and `secrets_ok` is false, `job.sh:69` refuses the item (`secrets not allowed on this branch`), which is the loud misconfiguration signal. The release a run writes to is fixed by the repo's own name and the state name or project, never taken from the file. No watch key `state` exists (Clarifications).

**State**

- **FR-020** `[error]`: WHEN a pipeline declares `[state]` and `FACTORY_CI_STATE_TOKEN` or `FACTORY_CI_STATE_KEY` is missing from Bitwarden (zero matches), or declares `[artifacts]` and `FACTORY_CI_STATE_TOKEN` or `FACTORY_CI_ARTIFACT_KEY` is missing, THE SYSTEM SHALL end the run with `[runner] state store not configured` before registering a ticket. Two matches, an empty value, a value with CR, LF or NUL, leading or trailing whitespace, or under 4 characters, are refused as for the four existing settings. A pipeline with `[state]` or `[artifacts]` also needs `FACTORY_CI_STATE_REPO` (the store repo, `owner/name`), and both keys must exist and differ, whichever of the two the pipeline uses: a missing key or equal values end the run the same way. A key (`FACTORY_CI_STATE_KEY` or `FACTORY_CI_ARTIFACT_KEY`) must be standard base64 or hex text that decodes to 32 bytes or more, with at least 8 distinct byte values in the decoded bytes. `[boundary]` A key that decodes to 32 bytes is accepted and 31 are refused. `FACTORY_CI_STATE_REPO` must have the shape `owner/name` (the 010 repo-name rule); anything else is `state store not configured`. A store 5xx during registration is retried inside the wait budget and does not print that line. On the tick the values arrive as the names-file variables (FR-066); a missing or bad one is `state store not configured` in the item status, and the frozen script refuses first when the Bitwarden key is absent.
- **FR-021**: WHEN the runner is the first in line and the state release has no asset THE SYSTEM SHALL start the pipeline with no state file at the declared path. This is the only case that starts empty.
- **FR-022** `[error]`: WHEN the newest state asset cannot be downloaded, authenticated or decrypted (wrong key, truncated, tampered, unreadable) THE SYSTEM SHALL end the run with `[runner] state restore failed`, start no container, change nothing in the store and release its ticket. It never falls back to an older asset or an empty state.
- **FR-023**: WHEN restore succeeds THE SYSTEM SHALL write the decrypted file at the declared path inside the checkout, mode 0600, immediately before the one step that declares it (`state = true`) starts, and remove it as soon as that step ends. No other step starts while it exists, and none sees it. Only the declared file is restored.
- **FR-024**: WHEN the pipeline passed THE SYSTEM SHALL read the declared file from the checkout and save it, encrypted with a fresh random nonce, as a new asset, before it removes the checkout. WHEN the file is missing THE SYSTEM SHALL save nothing and log a line to Loki. The runner reads the file right after the declaring step ends, after a root helper container has chowned the declared paths to the workspace owner (Clarifications, plan calls); a file it still cannot read is `state save failed`. It removes the file from the checkout at that moment and keeps the bytes in memory until the save. `[boundary]` A file of exactly 10 MB is saved. One of 10 MB plus 1 byte is refused (`[runner] state save failed`). A symlink at the path is refused.
- **FR-025**: WHEN a save uploads a new asset THE SYSTEM SHALL delete older assets only after the new one is stored and its size matches, and keep the 2 newest. WHEN restore sees several assets THE SYSTEM SHALL pick the newest by the store's order, not by name alone.
- **FR-026** `[error]`: WHEN the pipeline failed, was skipped in part, or hit a runner fault THE SYSTEM SHALL save no state. WHEN the pipeline passed and the upload or the size check fails THE SYSTEM SHALL end the run with `[runner] state save failed`, keep the previous state and release its ticket.
- **FR-027** `[error]`: THE SYSTEM SHALL encrypt every state file with an authenticated cipher under `FACTORY_CI_STATE_KEY` only, and every artifact bundle under `FACTORY_CI_ARTIFACT_KEY` only, so a changed byte fails decryption and one key never opens the other's assets. WHEN an asset is opened with the wrong one of the two keys THE SYSTEM SHALL fail authentication and return no plaintext. The state file is a credential: its content never enters an artifact (FR-018, FR-049, FR-050). No plaintext of either leaves the runner process or the checkout.

**Artifacts**

- **FR-028**: WHEN the pipeline did not pass and at least one step started, or `when = "always"`, THE SYSTEM SHALL bundle the declared paths that exist (a folder whole and recursive, a missing path skipped with a Loki line), scan the bundle (FR-049), encrypt it under the artifact key and upload it as one asset to the artifact release of the run's project in the repo that owns the pipeline. It runs after the pipeline, before the checkout is removed, and whether or not a step failed. It needs no ticket.
- **FR-029**: WHEN an upload completes THE SYSTEM SHALL log the release tag and the asset name to Loki as step `ci`, with the run id, and print nothing about them publicly.
- **FR-030**: WHEN an artifact upload completes THE SYSTEM SHALL keep the 10 newest bundles of that project's release and delete the rest. `[boundary]` With 10 bundles nothing is deleted. The 11th upload deletes the oldest.
- **FR-031** `[error]`: WHEN an artifact bundle or its upload fails THE SYSTEM SHALL log the cause to Loki as step `ci` and leave the run's exit code as the pipeline decided. It never turns a failure into a pass or a pass into a failure. The one exception is a refusal by the secret scan (FR-049), which ends the run with exit code 1.
- **FR-032** `[boundary]`: WHEN a bundle would exceed 100 MB THE SYSTEM SHALL upload nothing and log the size to Loki. 100 MB exactly is uploaded.
- **FR-033**: THE SYSTEM SHALL document one command line that downloads an artifact asset with `gh release download` and decrypts it, in `rust-ci-runner/README.md`. The key comes from the environment or standard input, never argv, and the doc names it by its Bitwarden name only. The same section states what an agent may hold: the artifact key, a Loki read token, and a GitHub token with contents read on the one private repo. It names what an agent must never hold (FR-048).

**Vault logins**

- **FR-042** `[error]`: WHEN a step declares a vault login THE SYSTEM SHALL accept only `vault = [{ item = "...", field = "...", env = "..." }]` on the step, entries with exactly those three string keys (item name, field name and environment variable name), and SHALL end the run with `[runner] pipeline file refused` before any vault call when the environment variable name breaks the 010 name rules, starts with `FACTORY_CI`, `BW_` or `BITWARDENCLI`, repeats in the step (across `env`, `secrets` and vault entries), or the step has `docker = true`. `[boundary]` A step may declare 20 fields and the pipeline 50; 21 and 51 are refused.
- **FR-043** `[error]` (0.4.1): WHEN the vault list returns any item that no declared `(item, field)` names THE SYSTEM SHALL end the item with the fixed text `vault item not allowed`, and WHEN a declared item matches zero or more than one login in the collection THE SYSTEM SHALL end it with `vault unavailable`; in both cases no container starts. Items match by exact name, case included. The `vault_items` watch key is dropped (Clarifications): the boundary is `main` only, the collection-limited account and the read of declared pairs only.
- **FR-044**: WHEN every declared item is allowed THE SYSTEM SHALL read all declared fields once, before the first container starts, and pass each value only to steps that declared it, through the environment of the engine child process, never argv. WHEN several steps declare the same item and field THE SYSTEM SHALL read it once.
- **FR-045** `[error]`: WHEN a declared item matches no login or more than one in what the identity can see, a declared field is missing, empty or holds a NUL, a value has a trimmed line under 4 characters, or the vault cannot be unlocked THE SYSTEM SHALL end the run with exit code 1, print exactly `[runner] vault unavailable`, and start no container. `[boundary]` A trimmed line of exactly 4 characters is accepted, 3 is refused. The vault settings missing from Bitwarden (`FACTORY_CI_VAULT_CLIENTID`, `FACTORY_CI_VAULT_CLIENTSECRET`, `FACTORY_CI_VAULT_PASSWORD`) end the run the same way. In runner 0.4.0 every validated vault declaration ends this way before a ticket (tick `job`, `local` and `ci` alike). From 0.4.1 the tick `job` reads the vault on `main` rows (the five vault names arrive by the names file); `local` and `ci` still end this way.
- **FR-046** `[error]`: WHEN the vault reads end, whether they succeeded or failed THE SYSTEM SHALL lock or log out of the vault and remove the `bw` session and data directory before any step starts, and SHALL give no `bw` child or step a session key, an unlock credential or the data directory path. WHEN lock, logout or removal fails THE SYSTEM SHALL end the run with `[runner] vault unavailable` and start no container.
- **FR-047**: THE SYSTEM SHALL add every vault value to the Redactor before any line that could hold it is written, with its base64 forms and each line of 4 or more characters, as for step secrets. The runner's own logs, stdout, stderr and Loki detail lines for the vault carry positions and counts only (for example `declared item 2 of 3`), never an item name, a field name or a value.
- **FR-048**: THE SYSTEM SHALL keep these out of reach of any agent and any step: the vault credentials, `FACTORY_CI_STATE_TOKEN`, `FACTORY_CI_STATE_KEY` and the Bitwarden access token. An agent's whole kit is `FACTORY_CI_ARTIFACT_KEY`, a Loki read token and a read-only GitHub token; no artifact, Loki line or public line may carry anything else.

**Artifact scan**

- **FR-049** `[error]`: WHEN a bundle is ready and before it is encrypted THE SYSTEM SHALL scan every file in it for each value the Redactor holds (the runner settings, step secrets, vault values, the Bitwarden access token, the FR-050 state strings, but not the numeric `FACTORY_CI_LOG_USER`, which is an identifier and matches digits by chance), each in its exact form, in the forms the Redactor knows (`Log::secret_forms`), and as each line of 4 or more characters of a multi-line value, and SHALL scan the contents of every zip entry, `trace.network` included, to a nesting depth of 2. WHEN a value matches, or a file cannot be scanned (an encrypted entry, depth over 2, more than 10,000 entries, more than 500 MB uncompressed, an unreadable file, a file that is not text, JSON, a zip with stored or deflate entries, PNG or JPEG, a member named `*.html`) THE SYSTEM SHALL upload nothing, print exactly `[runner] artifact upload refused`, end the run with exit code 1 and log to Loki only a position and a count, never the value, the matching file name or an offset. `[boundary]` A value of exactly 4 characters on one line is scanned for; a nested zip at depth 2 is scanned and one at depth 3 refuses the upload.
- **FR-050**: WHEN the state file is JSON THE SYSTEM SHALL add each string it holds under a key named `value` of 16 or more characters (the cookie and local storage values of a Playwright storageState) to the Redactor and to the scan set, and WHEN it is not JSON THE SYSTEM SHALL add its whole content when that is under 1 MB. It does this twice: for the restored bytes before the state step starts, and for the bytes the `after` hook reads when the state step ends, before any artifact is built, so a cookie issued during the run is masked and scanned too. `[boundary]` A 16-character cookie value is added, a 15-character one is not.

**Settings and containment**

- **FR-034** `[error]`: WHEN a watch entry lists any of `FACTORY_CI_STATE_TOKEN`, `FACTORY_CI_STATE_KEY`, `FACTORY_CI_ARTIFACT_KEY`, `FACTORY_CI_STATE_REPO`, `FACTORY_CI_VAULT_CLIENTID`, `FACTORY_CI_VAULT_CLIENTSECRET`, `FACTORY_CI_VAULT_PASSWORD`, `FACTORY_CI_VAULT_ORGID` or `FACTORY_CI_VAULT_COLLECTIONID` in `secrets` THE SYSTEM SHALL refuse the whole watch file. WHEN a pipeline lists any of them in `secrets`, or as a vault environment variable name, THE SYSTEM SHALL end the run with `[runner] pipeline file refused`. None of the nine values reaches a step, a step container argument, an engine child other than the one call that needs it, or a log body. The test list of 010 FR-004 grows from four names to thirteen, and 011 supersedes that list. Every name in a `secrets` list and every vault `env` name must be disjoint across the whole pipeline; a name in both is `pipeline file refused`.
- **FR-035**: THE SYSTEM SHALL mask all nine new values, their base64 forms and the base64 of `x-access-token:<token>` in every output path, as it does for the four settings, before any line that could hold them is written.
- **FR-036**: WHEN the runner calls `bw` THE SYSTEM SHALL give the call a time limit (60 s) and one retry, never after a rejected credential. WHEN the runner calls the GitHub API for the queue, state or artifacts THE SYSTEM SHALL use `FACTORY_CI_STATE_TOKEN` with a time limit, one retry on no answer or 5xx and a pause on 403 or 429, and never use `FACTORY_CI_TOKEN` for a write or `FACTORY_CI_STATE_TOKEN` for a clone. The token never appears in argv, a file or a git config.

**Public output**

- **FR-037**: WHEN the run prints THE SYSTEM SHALL keep stdout to the closed grammar of 008, extended by exactly one line, `[runner] waiting for the queue`, and stderr to the closed fault list, extended by exactly these lines: `queue wait expired`, `queue renewal failed`, `state not allowed`, `state store not configured`, `state restore failed`, `state save failed`, `vault item not allowed`, `vault unavailable`, `artifact upload refused`. No repo, branch, project, state, release, asset, vault item, vault field or secret name, and no count, position or age, appears in any public line. The lines join the closed list in `log.rs` and its test.
- **FR-061**: BEFORE any line that can carry a value and before any store call THE SYSTEM SHALL call `log.add_secrets` (the lines of steps 1 to 5 of the run order are fixed text and carry none) with the state token, the state key, the artifact key, the store repo name, `base64("x-access-token:" + state token)` and (0.4.1) the vault credentials, so no later line, Loki body, error text or asset can hold them. A test seeds each, plus the `x-access-token:` form, as canaries.

**Rollout**

- **FR-038**: THE SYSTEM SHALL release in two steps. Runner 0.4.0 carries the schedule, the ledger, the queue, state and artifacts on the tick path, reserves all 13 runner key names, parses and validates the vault declarations, and ends any validated vault declaration with `vault unavailable` before it registers a ticket or starts a container. Runner 0.4.1 adds the vault read (FR-044 to FR-047, FR-056) and the `bw` image. Each release: `Cargo.toml` and `Cargo.lock` agree, tag `rust-ci-runner-v<version>` on a commit on `main`, and the existing release workflow (unchanged) builds the image. `RUNNER_IMAGE` in `factory-monorepo-ci.yml` does not change. ### Key Entities

- **Schedule**: the `[schedule]` table of a pipeline file (`every`, `offset`); a slot is an epoch-aligned UTC instant.
- **Claim**: one 1-byte release asset `claim-<h16>-<slot>-<n>` in the repo's `ci-sched+` release of the store; its label holds the outcome letter (`r`, `p` or `f`), the epoch and the run id.
- **Watch entry**: gains no key. `secret_branches` (already accepted by 0.3.0), written as exactly `["main"]`, now also grants the store, state, queue, artifacts, vault and declared step secrets on the tick, for rows on `main` of a private repo. Reviewed on `main` of B. The dropped keys were `state` and `vault_items`.
- **Vault login**: a step's declaration of one item, one field and the environment variable that receives it. The values live in a Bitwarden Password Manager vault and reach only that step.
- **State**: one named file of a pipeline, stored encrypted in a release of the owning private repo, newest 2 kept.
- **Ticket**: a queue place of one run for one state, with a registration order and a renewal time. No cap per state.
- **Artifact bundle**: one encrypted archive of a run's declared paths, in the project's artifact release, newest 10 kept.
- **Runner settings**: `FACTORY_CI_TOKEN`, `FACTORY_CI_LOG_URL`, `FACTORY_CI_LOG_USER`, `FACTORY_CI_LOG_TOKEN`, now also `FACTORY_CI_STATE_TOKEN`, `FACTORY_CI_STATE_KEY`, `FACTORY_CI_ARTIFACT_KEY`, `FACTORY_CI_STATE_REPO`, `FACTORY_CI_VAULT_CLIENTID`, `FACTORY_CI_VAULT_CLIENTSECRET`, `FACTORY_CI_VAULT_PASSWORD`, `FACTORY_CI_VAULT_ORGID` and `FACTORY_CI_VAULT_COLLECTIONID` (thirteen in all, all held from the one `bws` call). Read by the runner, never handed to a step or an agent. The three vault credentials never leave the one `bw` call that needs them (0.4.1).
- **Agent kit**: the artifact key, a Loki read token and a read-only GitHub token. Nothing else.
- **Public line**: a stdout or stderr line from the closed grammar, now with one more stdout line and nine more fault lines.

## Success Criteria *(mandatory)*

### Hypothesis

If the runner keeps the browser session between runs and serializes the runs that share it, the Playwright project can log in once and not on every run, and an agent can diagnose a failure without the owner copying anything. We would be wrong if sessions expire faster than the runs come, if waiters time out, or if agents still ask the owner for more than the artifact. The first two cannot be measured until the pin moves (out of scope).

### Measurable Outcomes

- **SC-001**: A project with `every = "6h"` runs once per slot on the tick within 10 minutes of the slot (two ticks), never twice for one slot, and a slot missed by a tick failure runs on the next tick. Measured by the ten-tick fake walk of User Story 3 and, after the bump, by the Loki lines `claim created` and `claim passed` of one real day.
- **SC-002**: In the queue tests over the fake store, zero registered runs of one state are lost to anything other than `queue wait expired` and `queue renewal failed`, and no two overlap. Production loss by the concurrency group is out of scope. Measured by `queue_tests`.
- **SC-003**: A failed fixture run uploads one asset, Loki names it, and `decrypt-artifact` with the artifact key returns the file (User Story 4); the same holds for one real failed tick run after the bump.
- **SC-004**: Across a hostile fixture (canary state, token and key, artifact with a canary inside, step listing the settings), zero lines of stdout, stderr, child argv and Loki bodies hold a canary, no release asset holds a plaintext canary, and zero public lines hold a repo, state, release or asset name. Measured by the unit and fixture tests.
- **SC-005**: A failed run never changes the stored state: a test that fails the pipeline after a write to the state file finds the newest asset byte-identical to before.
- **SC-006**: `cargo test --lib` passes in the `rust-ci-runner` pipeline with tests for the in-scope requirements, and the releases publish a 0.4.0 digest (queue, state, artifacts) and a 0.4.1 digest (vault). Neither is pinned in the manual workflow (FR-038).
- **SC-007** (0.4.1): In a fixture run with a fake `bw`, the step's environment and visible files hold the declared variables and zero vault credentials, session keys or `bw` data. Zero runner log lines, public or Loki, hold a vault item name, field name or value. Measured by the fixture test and a search of every output.
- **SC-008**: Across a hostile artifact fixture (each known value in plain, base64, one line of a multi-line value, inside a zip and inside a nested zip), 100% of bundles are refused with no upload, and a clean bundle uploads. The state key opens no artifact and the artifact key opens no state asset. Measured by the unit tests.
- **SC-009**: The agent kit is documented (FR-033, FR-048) and the owner reviews it at the first real tick failure.

## Assumptions

- The owner creates the store repo and a fine-grained token scoped to it (contents write), the two keys (each `openssl rand -base64 33`, decoding to 32 bytes or more, different from each other), and the Bitwarden Secrets Manager entries for all of them and for the three vault settings. No code or doc holds a value. Anyone with write access to the Bitwarden project can read them all: that is already a trust root (008).
- The vault credentials unlock a Bitwarden Password Manager account. A Bitwarden API key belongs to a whole account, so limiting it to one collection takes a separate account that is a member of an organization with access to that collection only. The owner creates it; the spec recommends it (R12) and cannot enforce it.
- The `bw` command line client is not in the runner image today. The plan adds it pinned by SHA-256 like `bws`, or picks another way to read a vault, and justifies the size and the new dependency in Complexity Tracking. The `bw` call is a child process with a cleared environment holding only what it needs.
- The agent holds its own GitHub credentials for `gh`. The owner gives it a token with contents read on the one private repo. That token can download the encrypted state asset, which is useless without the state key.
- GitHub's store gives an atomic create that fails when the name exists (a ref or a release tag), server timestamps and release asset upload and delete. The plan picks the mechanism for tickets and renewals; this spec fixes only the behaviour. A queue operation that cannot be made atomic on GitHub is a blocker for the plan, not a reason to loosen FR-008.
- The runner has no encryption dependency today (`Cargo.toml` lists `getrandom`, `serde`, `serde_json`, `toml`, `ureq`). The plan chooses an authenticated cipher that the owner or an agent can open with a documented command, and justifies any new crate or image tool in Complexity Tracking.
- The state file is small (cookies, tens of KB). A directory as state, and a file over 10 MB, are out of scope.
- The step container runs as root. The state file is written at mode 0600 and the runner reads it after a root helper container chowns the declared paths to the workspace owner (Clarifications, plan calls), so a step may keep 0600 and no copy is world-readable.
- The tick workflow stays as it is. It has a plain lane (`run`) and a docker lane (`run-docker`); scheduled rows use the plain lane only.
- The pin of `factory-monorepo-ci.yml` stays on the image it names today (0.3.0). The tick reads `vars.RUNNER_IMAGE_DIGEST`, so the new binary reaches it with `gh variable set`. The frozen `factory-ci-job.sh` hands the final runner the names that its prepare mode lists, for rows whose `secrets_ok` is true, from Bitwarden keys `<repo><SEP><NAME>` of the plain lane's project (the entry has a numeric `id`).
- `sudtanj/infrastructure` and any public repo get no schedule, state or store access: the rule needs a private repo and `secret_branches = ["main"]`.
- The owner creates `<owner>/factory-ci-state` (private, no code, no workflows), seeds the ledger release `ci-sched+<owner>_<name>` for each scheduled repo (and the queue, state and artifact releases may be created by the job, which re-fetches on a race), adds it to the contents read scope of `FACTORY_CI_TOKEN`, and adds `<repo><SEP>FACTORY_CI_STATE_TOKEN`, `<repo><SEP>FACTORY_CI_STATE_KEY` and `<repo><SEP>FACTORY_CI_ARTIFACT_KEY` to the plain lane's Bitwarden project.
- Existing entries and pipelines with no `[state]` and no `[artifacts]` behave as before. The concurrency group, which stays, still serializes them (R4).

## Non-goals

- Queues for stateless pipelines, priorities, cancelling a queued run, and fair scheduling across states.
- Cron expressions, time zones, schedules on branches other than `main`, and catch-up of every missed slot.
- State as a directory, state shared between repos, state versions beyond the newest 2, rollback to an older state, and any merge of two states.
- Key rotation and re-encryption of old assets.
- Rewriting or masking text inside a bundle. The scan only refuses (FR-049).
- Scanning values the runner does not know: a secret that never passed through Bitwarden, a transformed value, or one split across lines (R2, R11).
- The vault TOTP code, attachments, secure notes beyond named fields, writing to the vault, more than one vault identity, and any per-field allowlist.
- Managing the agent's credentials, or checking what an agent was given. The spec fixes the kit and documents it (FR-033, FR-048).
- Streaming artifacts to Loki, viewing them in a browser, and any download tooling beyond one documented `gh` command.
- Docker steps with state, schedules for `allow_docker` entries and `docker/<name>` projects, `--allow-docker`, and any change to the tick workflow and its scripts.
- Any edit of a file under `.github/workflows/` or `.github/scripts/` (the owner rule), and with it the schedule, the pin bump of the manual workflow and a smoke step in the release workflow.
- A cap on step output, and any change to how the four existing settings are read beyond adding the others.

## Risks

- **R1, a write token on the runner**: `FACTORY_CI_STATE_TOKEN` can rewrite releases of every repo it covers. A pipeline cannot read it (FR-034), but a bug in the runner could leak it. Mitigation: fine-grained, only private repos with `state = true`, 90-day expiry like the others, masked, and never in a child environment.
- **R2, the queue is a lock on a public API**: a ticket that cannot be removed (token expired, API down) blocks the state until staleness frees it, and a stale break of a run that is alive but cut off from GitHub lets two runs overlap. Mitigation: 10-minute stale rule, the fence of FR-015 so the loser never writes state, and Loki lines for every break.
- **R3, an artifact holds secrets**: a Playwright trace records typed input and network traffic, so it can hold the login and cookies. Encryption protects the release from readers of the repo, not from whoever holds the artifact key, and the agent holds it. Mitigation: the scan of FR-049 reads every member including `trace.network` and refuses a bundle that holds any value the runner knows (the FR-050 state strings included); `.html` members and unreadable formats are refused; the artifact key differs from the state key; the state never enters a bundle. 002 keeps the HTML reporter off and scrubs its trace. A canary on a real failure trace runs before the first real run. The scan cannot see a value it does not know (R11).
- **R4, the concurrency group stays**: GitHub keeps one running and one pending run per repo, ref and project and cancels an older pending run when a third arrives, so a requested run can be lost before the runner starts. Mitigation: documented in the README. The queue behind the group adds no recovery for that case.
- **R5, the pinned manual `ci` cannot run a project that uses the new keys**: 0.3.0 refuses `[schedule]`, `[state]`, `[artifacts]`, `state = true` and `vault` (`pipeline.rs:10`, `:29`). Mitigation: the README says so, and the keys go into a project's toml only after the variable bump (FR-038). The earlier risk, features inert behind the pin, is gone: they run on the tick.
- **R6, the tick runner needs `GITHUB_RUN_ATTEMPT`, the row run id and a clone image that has `chown` and `chmod`**: the first two are set by Actions and `plan`; the helper image is `FACTORY_CI_CLONE_IMAGE`. A clone image without those tools stops a stateful run (`runner fault`, no ticket). Mitigation: an argv test, the canary of T029, and the job-limit test over both workflow files. (The earlier `docker inspect` of the runner container no longer exists.)
- **R7, waits are short**: a waiting job holds a runner for at most 5 minutes before `queue wait expired`; a run behind a long holder is dropped. Mitigation: the queue guards only what the concurrency group does not already serialize, and the drop is an alert built by hand.
- **R8, request order is approximate**: registration happens after the fetch, so near-simultaneous starts can swap (Clarifications). Mitigation: accepted. Strict order holds from registration on.
- **R9, rollout order**: the tick bump changes a live path. Mitigation: 012 merges first; the tick-path tests of FR-062 and FR-067 pass before the bump; record the old digest, bump after the tag and the digest check, watch two ticks (`fail_tick=0`, the same push statuses, no new public line), then the `secret_branches` pull request, then the Bitwarden keys and the owner actions, then the project toml keys. Rollback in reverse: remove the toml keys, then set the old digest back.
- **R10, one state per name per repo**: two pipelines of one repo that pick one state name share one queue and one file. Mitigation: pick distinct names.
- **R11, the scan is exact**: it finds known values in plain, in the base64 forms the Redactor knows and by line. A value a page renders differently (URL-encoded, split in a screenshot as pixels) passes. A screenshot of a page that shows a secret is an image, and no scan reads it. Mitigation: keep `when = "failure"`, declare only the paths that are needed, and treat artifacts as sensitive. A false positive (a 4-character value that matches ordinary text) blocks an upload and fails the run; the 4-character floor is the same as for masking.
- **R12, the vault credentials are a master key**: `FACTORY_CI_VAULT_CLIENTID`, `FACTORY_CI_VAULT_CLIENTSECRET` and `FACTORY_CI_VAULT_PASSWORD` unlock the account. Anyone who can read them from Bitwarden Secrets Manager, or reach the runner process memory, can read every item that account sees. The runner holds them only in memory and in one `bw` child, but the child's environment is readable by anything running as the same user in the container, as with the existing access token. Mitigation: a dedicated Bitwarden account in an organization that can see only the collection holding the allowlisted items, not the owner's personal vault; the `vault_items` allowlist; no step ever sees the credentials.
- **R13, allowlist is by item, not field**: a pipeline that may read an item may read every field of it. Mitigation: keep one item per purpose and put only the fields it needs in it.
- **R14, a vault read takes the turn**: reads happen inside the queue turn, so a slow vault holds the next run and cuts a late winner's window by up to 5 minutes. Mitigation: 60-second limit, one retry.
- **R16, a reviewed step can still print a transformed secret**: the redactor masks exact, base64, URL-encoded, JSON-escaped, hex and per-line forms. A step on reviewed `main` code that prints a value in another form (reversed, split, XOR-ed) is not masked. Accepted: the pipeline file and its steps are reviewed, `secret_branches` is `["main"]`, and the owner is told. A late winner also has a minimum pipeline window of 10 minutes (FR-052).
- **R17, the queue is seldom needed on the tick**: ticks run one at a time and one row exists per project per tick, so two waiters meet only on a tick rerun. Kept by the owner's word; droppable with no effect on state, claims and artifacts.
- **R18, the claim write token reaches the run job**: the store token sits in the run job's environment until the runner reads and removes it, and `::add-mask::` hides it in the log. It never reaches a step (engine children inherit seven fixed variables, `engine.rs:21`). A runner bug could leak it; it is scoped to the store repo, expires in 90 days and is masked by the runner's redactor. The same holds for the two keys.
- **R19, a failed label write after a pass repeats the slot**: the stale rule re-runs a slot whose claim stayed `r` for 3600 s once. At-least-once beats a lost run; the push walk makes the same trade (`walk.rs:11`).
- **R20, status cap**: a flapping schedule on an unchanged sha posts at most once an hour; the 1000-status cap needs about 42 days of flapping, and a 422 is ignored.
- **R21, the store name is in the public runner source**: `<owner>/factory-ci-state`. Private repos are listed by name in the public watch file already.
- **R22, a long scheduled run delays push CI**: the tick is serial, so every repo waits for the slowest item of the tick in front of it. A scheduled pipeline is capped at 10 minutes (FR-070), and the scan, upload, save and cleanup after it can add up to 15 more in the worst case; the worst-case delay of the next tick's push rows is about 25 minutes. Mitigation: the cap, the 15-minute floor, an alert on a tick over 20 minutes (FR-071), and the README says the cost; the owner may raise the cap (O21).
- **R23, the frozen status fallback does not know a row is scheduled**: it posts `error` for any refused, cancelled or unprepared item. Mitigation: `job::status` reads the push context first and routes by whether the latest own status there is `pending` (FR-073); tests pin the push context unchanged for the cancel, refuse and prepare-failure paths.
- **R24, a failure before the claim**: it cannot write a claim (no usable token yet). Mitigation: the schedule-context `error` backoff of `min(every, 3600 s)` (FR-074).

The budget end is read through `StatefulSeams.timing`, not straight from the environment.
- **FR-053** `[error]`: WHEN the runner lists tickets THE SYSTEM SHALL count only assets whose name matches the ticket pattern of contracts/release-store.md, count a non-`uploaded` asset that matches the ticket regex and is younger than 120 s by `created_at` as a live ticket, delete a non-`uploaded` asset of any other kind only once it is older than 360 s, treat a ticket whose label is missing, malformed or more than 120 s ahead of the reader's latest `Date` as stale, and log `overlap` at a renewal that sees a live ticket with a lower id. Retention counts only `uploaded` assets. `[boundary]` A label epoch 120 s ahead is accepted, 121 s is stale; a ticket-pattern asset 119 s old is live, 120 s is not; another kind at 360 s is kept, at 361 s deleted.

A renewal never pauses: WHEN renewals have failed for 600 s THE SYSTEM SHALL set a cancel flag, kill the run's step containers by their container-name prefix (`docker kill`), wait for them to exit, and only then delete the ticket, print `[runner] queue renewal failed` and exit 1. - **FR-060** ([013] partly superseded: 013 adds a cron line, a heartbeat gate and script changes to the tick; 011 itself still edits none): THE SYSTEM SHALL leave `.github/workflows/factory-ci-tick.yml`, its scripts and its settings unchanged. The state step runs as root; the README says so.

The `bw` server is the US cloud; the frozen tick script unsets `FACTORY_CI_BWS_SERVER_URL` before it starts the runner (`factory-ci-job.sh:115`), so the tick job cannot see it and always uses the US cloud; the README says so.

The Playwright HTML reporter must stay off in the pipeline (002 uses its own reporter).

WHEN a watch entry sets `allow_docker = true` and also lists `main` in `secret_branches` THE SYSTEM SHALL give its rows no store access (the docker lane has its own store project).

## Requirements from the owner tick decisions (FR-063 to FR-072)

- **FR-063**: THE SYSTEM SHALL keep the ledger in release `ci-sched+<owner>_<name>` of `<owner>/factory-ci-state`, as claim assets that match `^claim-[0-9a-f]{16}-[0-9]{1,12}-[01]$` with a 1-byte body and a label matching `^[rpf]\.[0-9]+\.[0-9a-f]{16}$` (`r` running, `p` passed, `f` failed; the pipeline outcome), order the claims of one `<h16>` by the `(slot, n)` parsed from the name and never by asset id, count only `uploaded` assets (a not-`uploaded` claim younger than 360 s counts as running, an older one is ignored by `plan` and deleted by the job), never read-modify-write a shared document, keep per `<h16>` the 2 newest `uploaded` claims after a claim ends, delete any claim older than 90 days by label epoch, and fail closed above 300 assets. The owner seeds the release once (owner actions); the job never creates it. A 404 on the tag, a 403 or an unreadable store is a plan problem and plans no scheduled row; it is never read as an empty ledger.
- **FR-064** `[error]`: WHEN a claim has label `r` and the latest `Date` is 3600 s or more past its epoch THE SYSTEM SHALL treat it as stale: `plan` plans the slot again with `n = 1` when `n` was 0, and the job creates `claim-<h16>-<slot>-1`. WHEN a stale claim has `n = 1` THE SYSTEM SHALL plan nothing and post one `error` status to the schedule context. A label that is missing, malformed or more than 120 s ahead of the reader's `Date` is stale. `[boundary]` 3599 s is running, 3600 s is stale; a label 120 s ahead is accepted, 121 s is stale; a `Date` skew of 2 s at a slot boundary never plans two rows for one slot. WHEN a job gets SIGTERM or SIGINT THE SYSTEM SHALL, within 5 s, delete its claim only while the claim is still `r` and no step has completed, and otherwise `PATCH` it to `f`, so a half-done run never repeats; the signal path reads the same completed-step flag as the step loop.
- **FR-065** `[error]`: WHEN `plan` needs the ledger THE SYSTEM SHALL read it with `FACTORY_CI_TOKEN` over the fixed host `api.github.com` with redirects off and a 30 s limit, after `GET /repos/<store>` answers `private: true`; WHEN the read fails, is rate limited, answers 403 or 404 for the store or the tag, shows more than 300 assets or returns a name or label outside FR-063 THE SYSTEM SHALL plan no scheduled row for that repo, add one problem line without names, and still plan its push rows. `plan` makes at most 4 ledger calls per repo per tick and at most 40 blob reads per tick.
- **FR-066**: WHEN the tick `job` runs in prepare mode on a row of branch `main` whose pipeline needs the store (it declares `[state]`, `[artifacts]` or `vault`, or the row is scheduled) THE SYSTEM SHALL list `FACTORY_CI_STATE_TOKEN` (plus `FACTORY_CI_STATE_KEY` for `[state]`, `FACTORY_CI_ARTIFACT_KEY` for `[artifacts]`, and in 0.4.1 the five vault names for `vault`) in the names file after the names the pipeline declared; WHEN the branch is not `main` THE SYSTEM SHALL list none of them. WHEN the final `job` starts THE SYSTEM SHALL read those variables once, remove them from its process environment before any thread or child exists, add them and the base64 of `x-access-token:<token>` to the redactor before any line or store call, and refuse a `FACTORY_CI_STATE_REPO` that differs from the derived name. WHEN any is missing, the job ends with the fixed reason `state store not configured` in the status. `plan` sets `secrets_ok` true on a row when its branch is `main`, its repo is private and the entry's `secret_branches` is exactly `["main"]`, or when 012's image rule says so.
- **FR-067**: THE SYSTEM SHALL grant store access, state, queue, artifacts, vault values and declared step secrets on the tick only to rows that satisfy the rule of FR-066 for `secrets_ok`. Declared step secrets on any other row keep the 010 tick behaviour (`NO_JOB_SECRETS`, the item refuses); state, queue, artifacts, vault and schedule declarations on any other row are ignored and the pipeline runs without them.
- **FR-068**: THE SYSTEM SHALL mark a scheduled row with `prev_sha` equal to `sha`; a push row never has that property (a test pins it). `plan` phase C posts no `pending` for a scheduled row and does not count it against the write cap; the `order` cap puts scheduled rows after push rows; a scheduled row for a (repo, branch, project) that has a push row in the same tick is dropped for that tick; the scheduled row's status context is `factory-ci-schedule[/<project>]` and no push context equals it or starts with it.
- **FR-069**: THE SYSTEM SHALL make the manual `ci` command refuse a pipeline that declares `[state]`, `[artifacts]`, `[schedule]`, `state = true` or `vault` with `[runner] state not allowed` before any store call or container. 0.4.x `ci` otherwise behaves as 0.3.0.
- **FR-070**: WHEN the tick job runs a stateful row THE SYSTEM SHALL take its attempt from `GITHUB_RUN_ATTEMPT` (digits, else `1`), use the row's `--run-id` for ticket, state and claim names, use `FACTORY_CI_CLONE_IMAGE` for the `chown` and `chmod` helper (`runner fault` if it cannot run them), and take the budget from the tick `run` job's 45-minute limit with the numbers of FR-052. A scheduled row's pipeline deadline is the smaller of 10 minutes from its start and the FR-052 deadline, because ticks are serial and a long scheduled run delays the push CI of every repo behind it; a pipeline that needs more is not a fit for the tick schedule (owner call O21, default 10 minutes).
- **FR-071**: THE SYSTEM SHALL write Loki step `ci` lines for the ledger: `claim created slot <s> attempt <n>`, `claim exists`, `claim passed`, `claim failed`, `claim finish failed`, `claim stale break`, `claim deleted on cancel`, `claim marked failed on cancel`, `claim half-created deleted`, `schedule silent exit <reason>` (nothing due or the claim was lost; a counter the alert rules watch), `schedule status skipped <reason>`; `plan` ships `schedule due <n> rows`, `schedule ledger unreadable`, `schedule backoff <n>` and `schedule ignored <n>` through its heartbeat line. No line holds a repo, branch, project, token or key. The alert file also carries: more than 3 `schedule silent exit` lines in a row for one project without a `claim created`, and a tick longer than 20 minutes (no plan heartbeat for 20 minutes, no data is Alerting).
- **FR-072**: THE SYSTEM SHALL keep every tick fault text public-safe: the fixed strings of FR-037 appear in the commit status description of the item, never a repo, branch, project, state, release, asset, item, field or secret name.
- **FR-073** `[error]`: WHEN the commit status of a tick item is posted by `job::status` (the frozen `status fallback` step, `factory-ci-tick.yml:203-209` and `factory-ci-status.sh:18-23`, after a refusal, a cancel or a failed prepare) or by `job` itself THE SYSTEM SHALL never write the push context for a scheduled row. `job::status` first reads the latest own status of the push context on the sha (`Api::status`, the token's own user): WHEN it is `pending` the item is a push row (the plan posts `pending` for every push row before it keeps it) and the `error` goes to the push context as before; otherwise the item is a scheduled row and the `error` goes to `factory-ci-schedule[/<project>]`; WHEN the read fails the status posts nothing and exits 1. `job` posts a scheduled row's final status by the rules of FR-004.
- **FR-074**: THE SYSTEM SHALL keep a failure before the claim from looping every tick: such a failure (an unusable token, a missing Bitwarden key, a refused or unparseable pipeline, `queue wait expired`) ends in an `error` status on the schedule context, and `plan` skips the project while that status is younger than `min(every, 3600 s)` (FR-002). A failure after the claim leaves the label `f` (FR-003).
